## [1.0.0] - 2026-11-25

First public release. Every component (control plane, node agent, desktop app, CLI, Terraform provider, Helm chart and images) ships under one version.

### Added

- **Control plane:** admin API, web UI, agent hub, Celery worker and a leader-elected scheduler over PostgreSQL 17 and Redis 7.4. Clusters, nodes, GPUs and a topology view, a model catalog with Hugging Face and ModelScope search, deployments with a scheduler dry run before placement, a model cache per node, benchmarks, alerts with channels, an audit log with CSV export, and IP rules for the admin and serving APIs. Sessions use HttpOnly cookies with CSRF protection, admin passwords use Argon2id, and API keys (`gd-...`) are stored as hashes and shown once.
- **API layer:** a serving API on its own process that speaks the OpenAI, Anthropic and Ollama formats, authenticates with API keys, and routes from an in-memory routing table with no database read on the hot path. It reaches nodes over mutual TLS and keeps working while the control plane restarts. Connections to each node are pooled, pre-warmed and kept open, and use HTTP/2 when the node offers it (HTTP/1.1 otherwise), so concurrent requests share one connection and a request over a long link pays no new handshake. Every deployment can also be called by its own name, so two deployments of one model can be targeted separately; `/v1/models` lists the deployment names whenever a model has more than one. The served OpenAPI spec of the admin API matches the published contract (paths, methods and operation ids, checked in CI).
- **Rules, layouts and swaps:** six rule types (time schedule, idle unload, high load grow, low traffic shrink, make room by priority, auto heal) with a history of every evaluation, including what was held back and why. GPU layouts such as Day and Night that switch on a schedule. Swaps that load, unload, move and restart step by step, persist their progress, resume on a new leader and roll back. A layout that makes models trade GPUs that cannot hold both copies unloads them first and then loads them on their new GPUs; other moves run after the swaps that free their target.
- **Node agent and vendor plugins:** a Rust agent that dials out to the hub, joins with a join token (one-time, or a multi-use enrolment token with a use limit and expiry, revocable and audited per join) and a certificate from the internal CA, rotates its certificate before expiry, and serves engines over an outbound tunnel to the API layer (or, opt-in, an mTLS proxy). Device plugins for Apple Silicon (verified on a Mac), NVIDIA (NVML, with an `nvidia-smi` fallback; implemented, awaiting hardware reports) and AMD, Hygon, MetaX, Moore Threads and T-Head (implemented against recorded vendor tool output, not yet verified on hardware), GPU slicing, health checks, a host firewall and an optional egress lock (pf on macOS, nftables on Linux; nftables verified in Linux containers, pf rendered and unit-tested) and engines that bind to localhost only. Engines outlive agent restarts, crashes and upgrades: on start the agent re-adopts every engine that is still healthy with its port unchanged and relaunches only what is gone, on its previous port, so an upgrade does not interrupt serving. `gpudeck-agent stop-engines` stops them on purpose, and `keep_engines_on_exit = false` stops them on a clean shutdown. In containers the agent image runs under `tini`, and an agent started as PID 1 reaps orphaned engine processes itself, so restarted llama.cpp routers leave no zombies.
- **Engines:** adapters, launch templates, flag presets and engine metrics for llama.cpp (including router mode), MLX, vLLM, vLLM-Omni, SGLang, SGLang Diffusion, TensorRT-LLM, MLX Audio, whisper.cpp, stable-diffusion.cpp and custom container engines. A pinned engine catalog with real sha256s: llama.cpp `b12500` with per-platform builds (macOS Metal; Linux CUDA 12.8 / 13.5 with the CUDA runtime bundle, ROCm, Vulkan and CPU) picked from the node's GPU, driver and glibc. On machines older than a build needs (most of those builds need glibc 2.38, Ubuntu 24.04), the agent uses an older pinned build (ROCm: `b10375`, built on Ubuntu 22.04), then the official llama.cpp image pinned by digest when Docker or Podman is installed, and otherwise refuses with a message that names what is missing (glibc, or a library found missing by `ldd` before start). llama.cpp cross-node pipeline parallel (head `--rpc`, workers `ggml-rpc-server`, flags checked against the release's `--help`), llama.cpp routers left without models stop after `router_idle_stop_seconds` (agent setting, default 120 s), and a model added to a router that already hosts others starts as its own server from the router's build (`router_overflow`) instead of restarting the router and reloading its models; engines are warmed up with a few requests before they report ready (`engine_warmup`, on by default for llama.cpp on NVIDIA), so first requests do not pay kernel compilation; native SGLang checks for the CUDA toolkit and `ninja` before loading and names what is missing; vLLM 0.34.0, vLLM-Omni 0.32.0, SGLang 0.5.23 and TensorRT-LLM 1.3.0 as official images pinned by tag and digest; MLX, mlx-audio and SGLang Diffusion in managed Python venvs from pinned wheels; whisper.cpp and stable-diffusion.cpp from pinned release assets (whisper.cpp built from its pinned source on macOS). Operator-installed engines (`engine_paths`) still win, also over a catalog engine whose default is its container image; nodes behind a port forward advertise their proxy port with `proxy_advertise_port`. llama.cpp and MLX are verified on an Apple silicon Mac; the other engines are implemented, awaiting hardware reports (tested against documented formats and recorded output).
- **SSH GPU instances:** hand a user an SSH container that has a slice of a GPU, with public keys only, a source CIDR allow-list (per instance or a cluster default; no CIDRs means nobody gets in) and sshd exposed only on the node's private interface. The default image, `ghcr.io/sur950/gpu-deck-ssh`, is Ubuntu with OpenSSH, so the host's `nvidia-smi` and driver libraries work inside; it is published with this release. CPU-only instances are verified with Docker on a Mac; GPU passthrough with MPS limits is implemented, awaiting hardware reports.
- **Cloud GPU VMs:** provision, list and manage GPU virtual machines on AWS, Azure, GCP and DigitalOcean from the Clusters screen; cloud-init installs the agent and joins the node. Implemented and tested against recorded provider API replies; not yet run against real cloud accounts.
- **Placement and local models:** placement counts the VRAM each instance really holds on each GPU, including the memory share vLLM, SGLang and TensorRT-LLM reserve and the slices of SSH instances, and the placement preview shows that figure with its reason. The node scanner imports a diffusers pipeline as one model and reads safetensors metadata (architecture, quantization, context length). The agent remembers the hashes of local model files by path, size and modification time, so a model is not hashed again on every load, and verifies new local files in the background while the engine starts.
- **Credentials vault:** typed credentials (cloud, Hugging Face, ModelScope, SSH, SMTP, webhook and more) encrypted with Fernet, write-only secret fields, a confirmed reveal endpoint, usage history for every use, `VAULT_KEYS` rotation with an hourly re-encrypt job, and protected system credentials.
- **Desktop app:** a Tauri 2 shell for macOS, Windows and Linux that loads a control plane's own web UI, with saved servers, native notifications, a tray with fleet health, `gpudeck://` deep links and a locked-down IPC surface. Verified on macOS; the Windows and Linux bundles are built by CI and not yet tested on those systems.
- **CLI:** `gpudeck`, a command for every admin API operation, built at runtime from the server's OpenAPI spec (cached per server and API version, with the contract bundled in the wheel as an offline fallback), so new endpoints appear without a CLI release and no client code is generated. Request bodies are validated against the schema before sending; table output on a terminal, JSON when piped, `-o yaml|csv`; profiles, and a session stored in the OS keychain.
- **Terraform provider:** resources for clusters, join tokens, models, deployments, layouts, rules, alert channels, API keys and IP rules, plus data sources for nodes, devices and engines.
- **Helm and Docker:** a Helm chart with migration hooks, PDBs, an HPA on the API layer, default-deny NetworkPolicies and ServiceMonitors (linted and rendered in CI, not yet installed on a live cluster), Docker Compose files for one machine (verified with Docker on a Mac), a hardened offline (air-gapped) bundle, and non-root images with a read-only root file system. Development dependencies run in Docker through `infra/scripts/bootstrap.dev.sh`.
- **Zero-touch deployment:** one published web image for any host name (its gateway serves the UI and forwards `/api`, including cookies, server-sent events and WebSockets, to the admin API set at runtime); the internal CA and the hub, API layer and control-plane certificates are created on first start; the control plane fetches node-agent builds from the matching GitHub release (checked against its `SHA256SUMS.txt`, cached, with `AGENT_DIST_DIR` as the offline override); and the agent hub serves everything a GPU machine needs (install script, builds, checksums, CA), so GPU machines only need outbound 8443 (and outbound 8444 for serving). The one-line installer pins the hub's CA before fetching anything.
- **Locked-down GPU machines:** a GPU machine trusts only the control plane it joined and, by default, listens on no port: the agent dials out to the API layer and inference requests travel back over that connection (HTTP/2, streamed unbuffered, with the same routing, drain, failover and in-flight accounting as the direct mode and no added latency on warm connections). The control plane pins its keys on every node through a security policy signed by its CA (hub and API-layer keys, tunnel endpoints, allowed source addresses), with key rotation that never locks a node out; forged, foreign or rolled-back policies are refused. The opt-in direct mode accepts only the API layer's key from allow-listed addresses, closes other sources before TLS, rate limits handshakes and binds to the private interface. The installers apply and verify a host firewall for the agent's ports (nftables / pf, never blocking the operator's SSH port; opt-out available), `--ca-fingerprint` is required to join, rejected connection attempts are reported per node and raise an alert in bursts, and `gpudeck-agent security audit` and `firewall status|apply|remove` show what a machine exposes. Verified with port scans and forged identities against Linux container nodes.
- **Kubernetes GPU nodes:** the agent DaemonSet enrols every node with one multi-use token, runs native engines out of the box and, when you opt in, runs container engines through the node's Docker-compatible socket.
- **Observed (external) engines:** list model servers GPU Deck did not start as `[[observe]]` entries in the agent's `agent.toml` (`url` for vLLM, SGLang, llama.cpp, TGI, OpenAI-compatible or any HTTP server, and/or a `log_file`) and they show up as **External** deployments with sessions, throughput, latency, KV cache, request mix, logs and their GPU memory. Strictly read-only: the agent only sends GET `/metrics`, `/health` and `/v1/models` or follows the log, never signals the process or binds its port; the scheduler, rules, layouts, swaps, routing, benchmarks and agent commands never act on them and changes answer `409 EXTERNAL_DEPLOYMENT`. Works on drained nodes; not billed.
- **Per-process GPU memory:** NVIDIA GPUs report the processes holding memory (NVML, pid, executable name and memory, never command lines). The GPU page lists them with the deployment or external server they belong to, the memory map shows memory used outside GPU Deck, and placement, new slices and the free figure count it, so nothing is planned into memory another process is using. GPU and node status comes from live data: busy with servers outside GPU Deck reads *Running (external)*, never *Idle*; a node whose agent is gone turns offline and shows red *Detached* (a drain it had is kept and shown, and undrain works while it is away), a connected drained node shows *Drained*, and a `node.offline` alert fires once a node has been silent for `NODE_OFFLINE_AFTER_SECONDS`. Memory sizes read in GiB on every screen and device properties are shown in plain words.
- **Observability:** Prometheus metrics for the control plane, API layer, agents and engines, Grafana dashboards and alert rules, per-deployment inference metrics (sessions, throughput, time to first token, end-to-end latency, KV cache) and live GPU load, VRAM, power and temperature.
- **Network latency, measured and used:** every API layer measures its round trip to each connected node over the path its requests take (the warm HTTP/2 connection or the agent's tunnel; one cheap probe every `SERVING_RTT_PROBE_SECONDS`, no extra round trip per request) and the agent hub times its WebSocket pings to every agent. The default `least_sessions` routing now sends each request to the replica with the lowest expected latency (round trip plus a load penalty): near-equal replicas share the load, the nearest one takes the traffic until it is busy and then requests spill over; failover is unchanged (`SERVING_LATENCY_ROUTING`, `SERVING_LATENCY_TOLERANCE_MS`). API layers carry a region label (`API_LAYER_REGION`, `API_LAYER_ID`), count requests per deployment and region, and placement prefers nodes close to the regions that carry a deployment's traffic and, for models split across nodes, nodes in the same cluster, zone and rack, with the reason in the placement preview (`SCHEDULER_LATENCY_AWARE`). Round trips are kept per minute (`LATENCY_RETENTION_DAYS`, migration `202_node_latency`), shown on the node list, a Network tab on the node page (now, p50 / p95 over a range, chart per API layer) and Observability › GPUs / infra, and served by `GET /metrics/latency/live` and `GET /metrics/latency`.
- **`Server-Timing` on serving responses:** route, queue, connect, rtt, net, engine, upstream and (non-streaming) total, with generic names that reveal no host or node by default (`SERVING_SERVER_TIMING=generic|detailed|off`); an AI gateway in front can read it. The node agent reports its own share in `x-gpudeck-proxy-timing`, which the API layer reads and removes. The full breakdown, with time to first token, is stored with each request, shown as "Where the time went" on Observability › Inference and served by `GET /metrics/request-timing`. Guidance on placing API layers next to the GPUs, per region behind a gateway or geo-DNS: [DEPLOYMENT.md](docs/DEPLOYMENT.md#network-latency-keep-the-api-layer-close-to-the-gpus).
- **Node agents update themselves, without model downtime:** when the control plane has a newer signed agent release, every node downloads it in the background through the hub it already talks to, verifies its sha256 and the release signature (ed25519, the public key pinned through the node's signed security policy) and keeps it staged; the running binary is untouched. Click **Update** on a node, start a **Rolling update** on a cluster (one node at a time, it stops at the first node that rolls back), or let a cluster update itself inside a maintenance window (days, hours, time zone). An update downloads nothing: it swaps the binary atomically and keeps the previous one, restarts the agent, which re-adopts the running engines with the same processes and ports, and checks that it reconnects healthy; otherwise the node rolls back by itself and an alert says why. The UI shows each node's version, staged version and the live steps (staged, swapping, restarting, re-adopting engines, health check, done or rolled back); while a node updates it shows **Updating**, its metrics pause for the restart and no offline alert fires. Root-owned installs get a small root update helper from the installers (systemd path unit, launchd daemon); Kubernetes nodes show **Managed by Helm** and are never updated in place; agents installed before this show **Update manually** once. Air-gapped control planes serve the release from `AGENT_DIST_DIR`. The release workflow signs `gpudeck-agent-<version>-manifest.json` with the `AGENT_RELEASE_SIGNING_KEY` secret (skipped with a warning when it is not set: such releases are never applied automatically); control planes trust `AGENT_RELEASE_PUBLIC_KEYS`. New: agent protocol commands `stage_update` / `apply_update` (capability-gated, the hub feature `agent_updates`), `gpudeck-agent update status|apply|install-helper`, the admin API *Agent updates* endpoints (also as CLI commands and the cluster's `config.agent_updates` in Terraform), migration `201_agent_updates`. Setup: [DEPLOYMENT.md](docs/DEPLOYMENT.md#agent-updates-and-the-release-signing-key).

### Known limitations

- GPU Deck is verified end to end on Apple silicon (llama.cpp, MLX), on an NVIDIA Hopper GPU (NVML monitoring, vLLM, the llama.cpp CUDA build, all three API formats, slices, routing, failover, auto-heal, idle unload, layout swaps, SSH GPU instances) and on Linux container nodes with simulated GPUs. SGLang and TensorRT-LLM ran on the NVIDIA GPU with the gaps below. AMD and the other vendors are implemented and tested against recorded fixtures, awaiting hardware reports. Fixes made after the NVIDIA run (engine re-adoption on agent restart, pooled HTTP/2 connections to the nodes, the outbound-only tunnel mode, among others) are covered by automated tests and await re-verification on a GPU. See [docs/TESTING.md](docs/TESTING.md) for what has run where.
- Native SGLang needs the CUDA toolkit on the machine (the container image includes it); TensorRT-LLM does not parse tool calls or reasoning yet and does not run on slices; in the Kubernetes DaemonSet the engines run in the agent's container and restart with it.
- Implemented but not yet verified on hardware: the AMD, Hygon, MetaX, Moore Threads and T-Head device plugins; NVIDIA MIG, Xid tracking and the `nvidia-smi` fallback; the vLLM and SGLang container images; the llama.cpp ROCm and Vulkan builds; the vLLM-Omni, SGLang Diffusion, MLX Audio, whisper.cpp, stable-diffusion.cpp and custom engine adapters; tensor and pipeline parallelism and multi-node placement on GPUs; the Kubernetes DaemonSet; the egress lock on a real host; and the AWS, Azure, GCP and DigitalOcean providers (tested against recorded API replies, not real accounts). Please share what you find with a [hardware report](https://github.com/sur950/gpu-deck/issues/new?template=hardware_report.yml).
- The pinned engine builds have not all been run on hardware (see above), and the Linux stable-diffusion.cpp builds need a glibc as new as Ubuntu 26.04's. The llama.cpp container fallback for older Linux systems and llama.cpp cross-node pipeline parallel are tested with unit and agent tests only. Air-gapped GPU machines cannot download engine builds; install engines there yourself (`engine_paths`). See [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).
- Latency-aware routing, the round-trip measurements and traffic-aware placement are tested over simulated links, not yet across real regions. Agent self-update is tested on macOS and in agent tests; the Linux systemd update helper awaits a run on real hardware. Signed agent updates need the release signing key (see [docs/RELEASING.md](docs/RELEASING.md)); a release built without it is never applied automatically.
- Downgrading across a database migration is not supported. Restore a backup instead.
- Usage metering, billing and cost reports from price plans, and request traces in the UI are planned for v2. Version 1.0.0 records request and token counters for the dashboard and the API key pages, but has no metering, billing, price plan or trace pages, admin endpoints, CLI commands or Terraform resources.
- Container engines on Kubernetes GPU nodes need a Docker-compatible socket on the node (Docker Engine or Podman); nodes with only containerd run native engines.
