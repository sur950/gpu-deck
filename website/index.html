Why GPU Deck

GPUs are the expensive part. Most fleets leave them idle or fight over them.

Inference servers get started by hand on one box at a time, models stay loaded all night, and nobody can say which team used which GPU hour. GPU Deck turns a pile of machines into one fleet you can schedule, automate and bill.

Problem 01

VRAM sits idle overnight

The daytime chat model holds the GPUs at 3 a.m. while the batch job waits.

Layouts switch whole sets of models by time of day, and idle models unload on their own.

Problem 02

One engine, one box, one script

vLLM here, llama.cpp there, MLX on the Mac, each started and restarted by hand.

One control plane picks the engine, places the model on the right GPUs and heals it.

Problem 03

No idea who used what

GPU cost is one line on an invoice, with no split by team, model or idle time.

Every request is metered per API key, model and node, and priced from your own plans.

GPU Deck is not an AI gateway. Put any AI gateway (LiteLLM, Kong, Portkey or your own) in front of it for users, quotas, rate limits and guardrails. GPU Deck authenticates API keys, routes to your GPUs and stores nothing about end users.

How it runs

One CPU server runs the deck. GPU machines just run the agent.

The control plane needs no GPU, no CUDA and no drivers: it is a handful of containers next to PostgreSQL and Redis. Every GPU machine gets the vendor driver and one native agent, which dials out to the control plane over mutual TLS and starts the engines on localhost.

  • mTLS request from the API layer to the agent proxy
  • Agent dials out to the hub (mTLS WebSocket)
  • HTTPS from your gateway or admins
  • Control plane, no GPU needed
Install once

On one CPU-only server

Docker with Compose, or a Kubernetes cluster with the Helm chart. Images come from GHCR, signed with cosign.

  • Web UI, admin API, API layer, agent hub, worker, beat and scheduler
  • PostgreSQL 17 and Redis 7.4, bundled or your own
  • Optional Prometheus, Grafana and OpenTelemetry
On every GPU machine

The driver and one agent

One command installs gpudeck-agent as a systemd (Linux) or launchd (macOS) service and joins it with a single-use token.

  • Engines start on 127.0.0.1, natively or in containers
  • Model files cached on the machine
  • Outbound 8443 to the hub; inbound 9443 from the API layer only
Optional, in front

Any AI gateway

Add GPU Deck as an OpenAI, Anthropic or Ollama upstream with a gd- key. Users, quotas and rate limits stay in the gateway.

  • /openai/v1, /anthropic/v1, /ollama/api
  • Serving API restricted to the gateway's IPs
  • Usage metered per API key

Agents dial out

GPU machines open no control port. Commands reach them over the agent's own WebSocket and are replayed after a reconnect.

Engines stay on localhost

Engines bind to 127.0.0.1. Only the agent proxy reaches them, and it accepts only the API layer's certificate.

Serving survives restarts

The API layer serves from an in-memory routing table, so upgrades of the rest of the control plane do not drop traffic.

Features

Everything between “I have GPUs” and “the API is up”, and what happens after.

One edition with every feature, from the first machine you join to the cost report at the end of the month.

01Fleet

Every GPU in one inventory, whatever the vendor.

Group machines into clusters, join them with a one-time token and see every accelerator with its VRAM, slices, load, power, temperature, driver and health. Topology shows which instance sits on which GPU.

  • Seven vendor plugins: NVIDIA, AMD, Apple Silicon, Hygon, MetaX, Moore Threads and T-Head.
  • GPU slicing, health checks and a model cache on every node.
  • Node certificates rotate before expiry; revoking one drops the node at once.

02Deploy

Pick a model. See where it lands before it loads.

Search Hugging Face or ModelScope, or scan a local folder. GPU Deck picks an engine for the format, the GPU vendor and the driver, runs a scheduler dry run of the placement, then deploys. Every deployment shows its replicas, live sessions, traffic weights and a ready-to-run curl.

  • Engines: llama.cpp (with router mode), vLLM, SGLang, TensorRT-LLM, MLX, MLX Audio, whisper.cpp, stable-diffusion.cpp or a custom container.
  • Least-sessions, round-robin or weighted routing; a failing replica is ejected and the request retried before the first byte.
  • GPU slicing, tensor and pipeline parallelism, launch templates, flag presets and benchmarks.

03Rules, layouts and swaps

Rules load, unload and move models so GPUs never sit idle.

Each rule is a short form that reads back as a sentence. Run it in dry-run first, then let it act; the history keeps every evaluation, including what was held back and why.

  • Layouts are named sets of models and replicas, such as Day and Night, applied on a timezone-aware, DST-safe schedule.
  • Safe swaps drain in-flight requests, unload, load and publish the new route, step by step. Progress is persisted, resumes on a new leader and rolls back on failure.

Six rule types

time_schedule

Time schedule

Apply the Day layout at 08:00 on weekdays, Night at 20:00, and prefetch models before the switch.

idle_unload

Idle unload

Unload a model after 30 minutes without requests, keeping a minimum number of replicas.

high_load_grow

High load grow

Add a replica when requests queue up or the KV cache fills for several minutes.

low_traffic_shrink

Low traffic shrink

Scale down, or move to a smaller GPU slice, when traffic stays low.

make_room_by_priority

Make room by priority

Evict an idle, evictable model when a higher-priority one needs the VRAM.

auto_heal

Auto heal

Restart, or move to another GPU, an instance that keeps failing health checks.

How a swap runs

  1. DrainStop new requests
  2. WaitIn-flight reaches zero
  3. UnloadFree the GPU
  4. LoadStart the new instance
  5. Roll backReload the previous one

05Observe

See inside every inference, down to the KV cache.

Sessions, throughput, time to first token, end-to-end latency and KV cache use for every deployment, next to live GPU load, VRAM, power and temperature. Logs, traces, audit entries and usage rows share one request id.

  • Prometheus metrics for the control plane, API layer, agents and engines.
  • Grafana dashboards for the GPU fleet, inference, usage and cost and the control plane, with alert rules.
  • OpenTelemetry traces, and alerts to Slack, email or signed webhooks.

06Meter and bill

Know what every GPU minute costs, including the idle ones.

Requests, tokens and GPU minutes per API key, model and node. Price plans turn them into cost per key, cluster, model and server, and time a model spends loaded but idle shows up as its own bucket instead of disappearing.

  • Token prices per node, cluster or default plan, with a separate rate for cached tokens.
  • Billable GPU time comes from uptime and is shared pro rata by tokens.
  • Monthly reports and CSV exports. Billing shows what the servers cost, nothing more.

Also in the box

The parts you would otherwise script yourself.

SSH GPU instances

Hand someone an SSH container with a GPU or a slice of one. Public keys only, an optional source CIDR allow-list, sshd only on the node's private interface, stopped by TTL.

Cloud GPU VMs

Launch GPU VMs on AWS, Azure, GCP or DigitalOcean from the Clusters screen. Cloud-init installs the agent and the node joins its cluster like any other machine.

Credentials vault

Typed credentials for clouds, model hubs, alert channels and SSH. Encrypted at rest, write-only secrets, an audited reveal and key rotation.

Audit log

Sign-ins, changes, rule actions and swaps: who, what, when and from where, with CSV export.

Alerts

Node, swap, rule and health events to Slack, email or HMAC-signed webhooks, filtered by severity.

High availability

Stateless APIs behind a load balancer, a leader-elected scheduler on Postgres leases, and swaps that resume on the new leader.

Model cache and benchmarks

Model files cached per node and prefetched before a layout switch. Benchmarks sweep concurrency against an SLO and can tune launch flags.

Offline install

An air-gapped bundle with images, the chart, agent builds, the CLI and a Terraform mirror, plus Hugging Face mirror support.

Desktop app

A native window around any control plane, with notifications and a tray. More

IP rules

Allow and block lists for the admin and serving APIs, cached in memory, and refused if they would lock you out.

CLI, Terraform, Helm

Run it from code, not just from the UI.

Get started

From a CPU server to your first API call.

Four steps. The commands below are the short version; the deployment guide has every setting, the HTTPS setup and the checks.

  1. 1

    Start the control plane

    CPU-only server

    Any Linux server (or a Mac) with Docker and the Compose plugin. Fill the CHANGE-ME values in the .env (secret key, vault key, admin password and the hub URL your GPU machines will reach), then start it.

    control plane 
    git clone --depth 1 --branch v1.0.0 https://github.com/sur950/gpu-deck.git
cd gpu-deck
cp apps/fastapi/.env.example apps/fastapi/.env   # replace every CHANGE-ME
export GPUDECK_VERSION=1.0.0
export COMPOSE_FILE=infra/docker/docker-compose.yml:infra/docker/docker-compose.full.yml
docker compose pull
docker compose --profile tools run --rm migrate
docker compose up -d                  # web UI on :3180, serving API on :8181
    # Bring your own PostgreSQL 17 and Redis 7.4; secrets go in a Secret
kubectl create namespace gpu-deck
kubectl -n gpu-deck create secret generic gpu-deck-env --from-env-file=prod.env
helm upgrade --install gpu-deck oci://ghcr.io/sur950/charts/gpu-deck \
  --version 1.0.0 -n gpu-deck \
  --set secrets.existingSecret=gpu-deck-env -f my-values.yaml
# the agent hub is a LoadBalancer Service on TCP 8443, never an HTTP ingress
    # on a connected machine
infra/offline/build-bundle.sh --version 1.0.0 --with-data-services
# on the site, after copying the bundle
./install.sh verify
./install.sh load-images --registry registry.local:5000/gpu-deck
./install.sh compose --env /etc/gpu-deck/.env --full    # or: ./install.sh helm
  2. 2

    Add a GPU machine

    each GPU machine

    Install the GPU driver, then open Nodes, Add node. You get a single-use join token (15 minutes) and a one-line install command. Run it on the machine: it installs gpudeck-agent as a service, gets a certificate from GPU Deck's own CA and dials out to the hub.

    The machine needs outbound port 8443 to the control plane, and accepts inbound 9443 from the API layer only.

    GPU machine 
    # Paste the one-line command from Nodes, Add node. It installs the
# agent as a systemd (Linux) or launchd (macOS) service, then runs:
gpudeck-agent join --hub https://gpudeck-hub.example.com:8443 \
  --token gdj_… --ca-fingerprint <sha256>
# the node shows up online, with its GPUs, within seconds
  3. 3

    Deploy a model

    web UI or CLI

    In Catalog, search Hugging Face or ModelScope (or scan a local path) and press Deploy. The wizard picks the engine and shows the placement; the agent downloads the files, starts the engine on 127.0.0.1 and the instance turns ready.

    terminal 
    # the same from a terminal
cat > deploy.yaml <<'EOF'
name: qwen3-chat
model_id: <id from the catalog>     # gpudeck models list
replicas: 1
max_replicas: 2                   # no engine set: GPU Deck picks one
EOF
gpudeck deployments create -f deploy.yaml --set dry_run=true   # placement preview
gpudeck deployments create -f deploy.yaml
  4. 4

    Create a key and call it

    anywhere

    Create an API key under API keys. The gd- key is shown once and only its hash is stored. Give your AI gateway its own key, or one per team, and usage and cost are split the same way.

    first request 
    curl http://127.0.0.1:8181/openai/v1/chat/completions \
  -H "Authorization: Bearer gd-…" -H "Content-Type: application/json" \
  -d '{"model":"qwen3-0.6b","messages":[{"role":"user","content":"hi"}]}'

Just want to look around? Clone the repository and run the web UI on its built-in fixtures with NEXT_PUBLIC_API_MOCKS=1 pnpm --filter web dev, or start the full stack with ./infra/scripts/bootstrap.dev.sh. Details in the development guide.

Security

Deny everything, then open only what inference needs.

Nothing on a GPU machine is reachable from the internet. Every rule in the network model maps to where it is enforced in code, the chart and the Compose files.

Mutual TLS between machines

Agents present a certificate to the hub; the agent proxy accepts only the API layer's certificate. TLS 1.3 on the hub.

Single-use joins, own CA

Join tokens expire in 15 minutes. Certificates rotate 30 days before expiry and a revoked one drops the node at once.

Encrypted credentials vault

Fernet with key rotation, write-only secret fields, a confirmed and audited reveal, and usage history for every read.

Audit everything

Admin, rule, swap, key and vault actions with actor, IP, user agent, request id, before and after.

No end-user data

GPU Deck knows API keys, not people. Usage rows hold counts and timings, not prompts or completions.

Hardened admin

Argon2id passwords, HttpOnly sessions with CSRF protection, login lockout and IP allow and block rules.

Locked-down nodes

Engines bind to localhost, and an optional egress lock (pf or nftables) limits downloads to your model hubs.

Signed, minimal images

Non-root containers with a read-only root file system, cosign signatures, provenance and SBOMs.

FAQ

Questions people ask first.

Something else? Ask in GitHub Discussions.

Does the control plane need a GPU?

No. The control plane is a set of CPU-only containers plus PostgreSQL and Redis. A small server (4 vCPU and 8 GB of RAM is a reasonable start for up to five GPU machines) or a Kubernetes cluster is enough. GPUs live only on the machines that run the agent.

What exactly do I install on a GPU machine?

The vendor driver, and the node agent through the one-line command from the web UI. The agent downloads llama.cpp itself; for MLX, whisper.cpp and similar engines you install the binary, and for vLLM, SGLang or TensorRT-LLM a container runtime. Models are downloaded and cached by the agent.

Is GPU Deck an AI gateway?

No. It authenticates API keys, routes requests to your GPUs and meters them. Users, quotas, rate limits and guardrails belong in an AI gateway in front of it, such as LiteLLM, Kong, Portkey or your own. Give the gateway its own gd- key, or one per team.

Does GPU Deck see my users' prompts?

Requests pass through the API layer to your engines, but GPU Deck stores nothing about end users. Usage rows hold counts and timings (tokens, GPU seconds, latency) per API key, model and node, not prompts or completions.

Which hardware has actually been tested?

Apple Silicon end to end, with llama.cpp and MLX. NVIDIA, AMD and the other vendor plugins, the container engines, multi-node placement and the cloud providers are tested against recorded fixtures. If you run any of them, please file a hardware report.

Can it run without internet access?

Yes. The offline bundle carries the images, the Helm chart, the agent builds, the CLI and a Terraform provider mirror. Point the agents at a Hugging Face or ModelScope mirror, or use local model files.

How do upgrades work?

Every component ships under one version. Upgrade the control plane first (migrations run forward, and the API layer keeps serving meanwhile), then the agents node by node. A control plane works with every agent of the same protocol major.

How does it relate to GPUStack?

GPU Deck includes ideas and some code adapted from GPUStack (Apache-2.0), such as accelerator detection and placement heuristics; the NOTICE carries the credit. GPU Deck adds rules, layouts, swaps, deep inference metrics, metering and billing.

Is there a paid or enterprise edition?

No. There is one edition with every feature, under the Apache License 2.0.
